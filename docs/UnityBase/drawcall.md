# UGUI 合批与 DrawCall 优化

## 文档简介

UI 卡顿很少是"绘制太慢"，多数时候是 **DrawCall 太多导致 CPU 侧提交压力过大**。而 UGUI 的 DrawCall 数量，本质上由**合批是否被打断**决定。

本文把实习中做的 UI 侧 DrawCall 优化整理成一套可复用的排查流程。

---

## 1 先理解合批

### 1.1 DrawCall 是什么

CPU 每提交一次绘制指令（设置材质、传参数、下发网格）就是一次 DrawCall。数量越多，CPU 开销越大，主线程越容易卡。

### 1.2 UGUI 的合批规则

UGUI 的每个 `Graphic`（Image / Text / RawImage）会生成一个网格。相邻的、满足以下条件的网格会被合并成一次 DrawCall：

| 条件 | 说明 |
| --- | --- |
| 使用同一张图集（同一材质） | 纹理不同 → 必须分两次画 |
| 在层级中**连续** | 中间插入别的材质 → 批次被打断 |
| 不使用会打断合批的组件 | `Mask`、`RectMask2D`、`TMP-Sprite` 子网格等 |

一句话：**合批是按层级顺序累积的，一旦遇到不兼容的邻居，前面攒的批次就要提交，然后重新开始攒。**

---

## 2 常见打断合批的诱因

| 诱因 | 表现 | 处理 |
| --- | --- | --- |
| **图集不统一** | 同屏 UI 元素来自十几张小图 | 按界面/模块合并图集，一屏尽量控制在 1-2 张 |
| **层级穿插** | A 图集的元素和 B 图集的元素交替排列 | 调整同级元素顺序，让同图集的连续排列 |
| **材质不一致** | 自定义 Shader、描边、灰度材质混用 | 统一 UI 材质，必须用特殊材质时集中放置 |
| **TMP-Sprite 子网格** | 文本里混图文，每个 Sprite 单独一次绘制 | 减少文本内嵌图，或改用独立 Image |
| **Mask / RectMask2D** | 遮罩会切断批次 | 能用 RectMask2D 就不用 Mask；遮罩范围尽量小 |
| **透明排序需求** | 半透明元素必须按序绘制 | 接受必要的额外批次，不要为压数字牺牲正确性 |

## 3 排查流程

### 3.1 先量化

| 工具 | 用途 |
| --- | --- |
| **Frame Debugger** | 逐次查看 DrawCall，清楚看到哪一步被打断、原因是什么 |
| **Profiler → Rendering** | 看 Batches / SetPass Calls 的总体趋势 |
| **Stats 面板** | 快速看 Batches 数量随界面变化的波动 |

### 3.2 定位步骤

```
1. 打开目标界面 → 记录 Batches 基线
2. Frame Debugger 逐条走 → 找到"批次重启"的位置
3. 看该位置前后两个元素的 图集 / 材质 / 层级
4. 判断属于哪类诱因（图集 / 顺序 / 材质 / 子网格 / 遮罩）
5. 针对性调整 → 重新量化对比
```

**关键**：不要一上来就改代码。先把"哪一次提交是多余的"找出来，再决定改图集还是改层级。

---

## 4 优化手段

### 4.1 规整图集

- 同一界面的元素尽量来自同一张图集
- 小图标合并进公共图集，避免每张图单独打包
- 注意图集尺寸上限（移动端常见 2048×2048），别为了合并把图集撑爆

### 4.2 调整层级顺序

```text
优化前（图集 A / B 交替）：
  Bg(A) → Icon1(B) → Icon2(A) → Icon3(B) → Text(A)
  → 批次被反复打断

优化后（同图集连续）：
  Bg(A) → Icon2(A) → Text(A) → Icon1(B) → Icon3(B)
  → A 图集一次画完，B 图集一次画完
```

前提是**视觉层级允许**。如果 B 图集的元素必须压在 A 上面，就只能接受这次打断。

### 4.3 减少不必要的 Graphic

| 做法 | 收益 |
| --- | --- |
| 纯色块用 `Image` 配 1×1 白图，不单独出图 | 省图集空间 |
| 静态背景合并成一张大图 | 减少 Graphic 数量 |
| 隐藏的界面及时 `SetActive(false)` | 不参与合批计算 |
| 列表项用对象池，只保留可视区 | 大幅减少 Graphic 总数 |

### 4.4 文本

- 同一个界面尽量统一字体与字号，减少 TMP 材质变体
- 避免大量 `Outline` / `Shadow` 组件（每个都会额外生成网格）
- 长列表用虚拟化，不要把上千条文本全部实例化

---

## 5 效果衡量

优化后对比这几个数字，而不是凭感觉：

| 指标 | 说明 |
| --- | --- |
| Batches | 该界面的合批后批次数，最直接的指标 |
| SetPass Calls | 材质切换次数 |
| CPU Main Thread | UI 提交占用的主线程时间 |
| 帧率稳定性 | 滑动列表时的掉帧情况 |

经验值：普通界面把 Batches 压到 **20 以内**，复杂界面（背包、图鉴）控制在 **40 以内**，移动端一般就比较从容了。

---

## 6 小结

| 阶段 | 动作 |
| --- | --- |
| 认知 | 合批是按层级顺序累积的，打断就重新攒 |
| 量化 | Frame Debugger 找"批次重启"的位置 |
| 归因 | 图集 / 顺序 / 材质 / 子网格 / 遮罩 五类 |
| 优化 | 合并图集、调整同级顺序、减少 Graphic、列表虚拟化 |
| 验证 | 对比 Batches 与主线程耗时，而不是靠体感 |

DrawCall 优化没有银弹，本质是**把同材质的元素排到一起，把不需要画的东西别画**。先定位再动手，比盲目改图集有效得多。
